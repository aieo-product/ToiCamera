# Unit CamS3 firmware

Custom build of the M5Stack factory firmware with a small STA-server patch,
so the camera serves its REST API while joined to the watch's SoftAP.

## Provenance & license

Patches apply on top of
[m5stack/UnitCamS3-UserDemo](https://github.com/m5stack/UnitCamS3-UserDemo)
(branch `unitcams3-5mp`, for the 5MP variant), licensed under the
**MIT License, Copyright (c) M5Stack**. The `patches/*.patch` files include
short excerpts of that code as diff context.

- `0002-sta-retry-reboot.patch` — the patch `build.sh` applies: starts the
  HTTP server in STA mode, falls back to the factory AP after a 30s connect
  timeout (pairing window), and reboots after 3 minutes to retry STA so a
  camera that boots before the watch doesn't stay stuck in AP mode.
- `0001-toicamera-sta-server.patch` — earlier revision of 0002, kept for
  reference.
- `0003-esp_insights-sha_size-build-fix.patch` — documents the esp_insights
  `SHA_SIZE` build fix for ESP-IDF v5.1.4; `build.sh` applies it inline
  because `managed_components/` is regenerated by `fetch_repos.py`.

## Why a custom build

The factory firmware only serves its REST API in AP mode (`UnitCamS3-WiFi`,
192.168.4.1). In STA mode it runs the EzData poster flow and **no HTTP
server** — so out of the box the watch could not pull frames from a camera
joined to its SoftAP. The patch adds an STA-mode server with the same API.

## Build & flash

```bash
# Prereq: ESP-IDF v5.1.4 at ~/esp/esp-idf
#   https://docs.espressif.com/projects/esp-idf/en/v5.1.4/esp32s3/get-started/
./build.sh          # clone factory repo + apply patch + build
./build.sh flash    # + erase config & flash (CamS3 on USB-C)
```

`erase-flash` wipes the stored WiFi config, so the camera boots in AP mode
and the watch pairs it automatically (see the pairing flow in
`docs/DESIGN.md` §4.2). No router/LAN setup is needed — the camera joins the
watch's SoftAP `ToiCamera` and is discovered via its DHCP lease.

## REST API (same as factory)

| Endpoint | Use in ToiCamera |
|---|---|
| `GET /api/v1/capture` | still JPEG — the watch polls this |
| `GET /api/v1/control?var=<k>&val=<v>` | `framesize`/`quality`/`awb`/`aec`/`agc`/`vflip`/`hmirror`… |
| `GET /api/v1/status` | sensor state (JSON) |
| `GET /api/v1/led_on` / `led_off` | capture LED feedback |
| `POST /api/v1/set_config` | `{wifiSsid, wifiPass, ...}` → STA mode on reboot |
| `GET /api/v1/stream` | MJPEG (VGA ≈11fps) |

### ⚠️ Sensor gotchas (PY260 / mega_ccm driver)

- Factory defaults ship with `awb/aec/agc` **all OFF** → captures average
  luminance ~3/255 (near-black). The watch fixes this at boot via
  `configureCamera()` (awb=1, awb_gain=1, aec=1, agc=1, gainceiling=2).
- Supported frame sizes are the sensor-real modes only (QVGA/VGA/HD/UXGA/
  FHD/5MP + the 96/128/320 squares); other init tables produce corrupt
  output. `quality` is 3-step (0=high, 1=default, 2=low). **Unsupported
  values return "ok" without touching the sensor** — verify with
  `/api/v1/status`, not the control response.

## Power

No battery on board. Grove red=5V / black=GND from the Stopwatch powers it
(200–400mA peaks). The Grove data pins are **USB D+/D- (G19/G20)** — do not
drive UART signals into them. The Stopwatch enables its PMIC-gated 5V output
at boot (`cfg.output_power` / `M5.Power.setExtOutput(true)`).
